综述

2022 年以来，以 Triton、vLLM、FlashInfer 为代表的工程系统显著降低了 GPU 算子开发与 LLM 推理引擎构建的门槛。然而，这些系统本身又提出了一个更难的问题：谁来优化这些优化器？

大语言模型 agent 的出现为这个问题提供了新范式。从最初的"LLM 写 CUDA 代码 + 编译反馈修正"的单 agent 闭环，演化到"多角色分工 + 持久知识文件"的团队，再到最近"让 agent 自己改写整个推理引擎"的系统级自演化，四年间这一方向经历了从工具到同伴再到宿主的三层跃迁。

本综述覆盖五条主线： ① Agent 优化 CUDA/Kernel 算子（16 篇核心论文）； ② Agent 优化 LLM 推理引擎（让 agent 改 FlashInfer / SGLang / vLLM 本身）； ③ Agent 优化推理调度与服务层（KV cache、speculative decoding、agentic serving）； ④ 基础方法谱系（Reflexion → EAT 演化）； ⑤ RSI 递归自我改进（Recursive Self-Improvement：从 Gödel Machine 到 DGM / HGM / SEAL，再到 2026 年的 AREX、Terminal-RSI、SwarmRSI）。

论文入选标准：① 直接使用 LLM agent 或类似 agentic 框架优化目标；② 有可验证的实验结果；③ 2022–2026 年发表于顶级会议 / 主流 arxiv 预印本。剔除了仅用 LLM 作为 prompt generator 但没有反馈闭环的工作。

本文覆盖的论文分类占比

五个方向合计约 48 篇核心论文（不含被引用但未直接优化目标系统的基准工作；部分工作跨类重复计入）。算子优化方向最活跃（16 篇），因为目标相对可界定、评测容易自动化；推理引擎方向虽然起步晚（SEIS 2026.10）但影响力最大——3.27× throughput 对整个领域是"存在性证明"级别的结果；RSI 方向文献量最大且增长最快（20 篇），但绝大多数集中在通用 agent / 代码 / 模型权重，尚未下沉到算子与推理引擎。

基础方法谱系提供了更广阔的方法论背景——Reflexion / Voyager / FunSearch 不直接优化算子或引擎，但其演化思路是 EAT / SEIS 的直接祖先；RSI 则提供了"为什么可以反复自我改进"的理论骨架。

时间线 · 四阶段演化

从 2022 年的传统 autotuning 到 2026 年的多 agent 系统级自演化，可清晰划分为四个阶段。图中另加一行 RSI 自我改进，因为它不是某个阶段，而是贯穿全程的方法论基座——2024 年 Gödel Agent / ADAS 起步，2025 年 DGM / HGM / SEAL 成型，2026 年出现以 RSI 命名的预印本潮。

第一阶段：传统 autotuning（2022）

基线建立。AutoTVM、Ansor 等基于 TVM 的系统使用基于 cost model + evolutionary search 的自动调优，无 LLM 参与。同期 Triton、FlashAttention 发布，为后续 LLM agent 提供了可编辑目标。

第二阶段：LLM 单 agent + 编译反馈（2023–Early 2025）

LLM 初登场。KernelBench 奠定评测基准；CUDAForge、OptiML 等采用"生成 → 编译 → 剖析 → 再生成"的单 agent 闭环，典型加速 1.4–1.7×。核心局限：agent 独立探索、知识不持久、容易陷入局部最优。

第三阶段：多 agent + 持久知识（Late 2025–2026）

团队登场。EAT 演化型团队、KernelOPT 引入 Inductor-aware dispatch 感知、CUDA Agent 大规模 RL、KernelFalcon 深度 agent 架构。从"让 agent 写 kernel"变为"让 agent 组织团队写 kernel"，配合 LEARNINGS.md / SYNTHESIS.md 持久化知识。

第四阶段：系统级自演化（2026）

从算子走到引擎。SEIS 让 agent 改写整个 mini-sglang 引擎（3.27× throughput）；FlashInfer-Bench 构建安全 kernel substitution 闭环；FlashNext-RL 研究长时程 agentic RL 的系统优化。agent 从"工具使用者"变为"宿主改写者"。

A · 1

算子优化 · Agent 写 CUDA Kernel

这是最活跃的方向。输入是 Python/PyTorch/Triton 伪代码或数学表达式，目标是生成高性能 CUDA/Triton kernel。反馈机制从编译正确性 + 运行时间逐步扩展到 Nsight Compute (NCU) 硬件剖析、Amdahl 定律加权、五级正确性 harness、Inductor dispatch 感知。

B · 2

推理引擎 · Agent 改写整个系统

相比算子优化在已知框架（Triton/Inductor）里填 patch，系统级优化让 agent 面对整个推理引擎源码。这要求 agent 不仅能改 kernel，还能改 Python runtime、scheduler、KV cache 管理、CUDA graph 策略等跨层边界。

SEIS · Self-Evolving Inference Systems

Xu, Liu, Li, Rabbani, Zhang · University of Chicago · 2026 · arxiv:2610.04646
目标
mini-sglang 整个引擎（Qwen3-0.6B on H100）
架构
固定 agent + Branching / Branching Chain / Sync Branching Chain 三种演化拓扑。每个 session 2 小时墙钟硬限；通过 numerical precision gate（perplexity ±5%、KL ≤ 0.05、argmax ≥ 90%）和 downstream performance gate（GSM8K、long-input retrieval）过滤代码；code + report 在 session 间继承
速度
3.27× vanilla mini-sglang throughput；在单请求负载上超过 vLLM、TensorRT-LLM、SGLang SOTA 配置
引擎演化路径
量化 kernel → 算子融合 → 执行 overhead 削减 → speculative decoding（经历 提出→拒绝→重测→最终实现 路径）；speculation 禁用时多数加速仍保留（ordinary decoding 本身被重写）
其他发现
① 继承 session 胜过独立尝试；② Sync Chain 中 agent 选择性接纳外部设计；③ 仅 numerical gate 不足以保证 task accuracy（GSM8K +1.06pp，retrieval -0.37pp）——agent 有"numerical reward hacking"；④ 评测本身也需要演化
arxiv

意义
让 EAT / KernelOPT / CUDAForge 等 agent-generated kernel 不只是 paper 上的 benchmark 数字，而是能进真实 serving 系统

D · 4

基础方法谱系 · 从 Reflexion 到 EAT

算子优化和推理引擎优化共享一组来自更广范围的 LLM self-improvement 方法。理解这条谱系对把握"agent 为什么能优化系统"至关重要。

Reflexion → Voyager → FunSearch → AlphaEvolve → EAT → SEIS

2023 → 2026 · 方法学演化链
Reflexion (2023)
让 agent 把 verbal feedback 积累起来反思。首次证明"反思 + 再尝试"优于"硬编码修复 + 再尝试"
Voyager (2023)
Minecraft 中的持续学习 agent，构建 growing skill library。EAT 的 LEARNINGS.md 可以看作 Voyager skill library 的结构化重实现
FunSearch (2024)
种群式演化搜索 + LLM 驱动变异。岛模型：独立搜索岛屿，周期性把较弱岛屿 re-seed
AlphaEvolve (2025)
延续 FunSearch 范式但规模更大。EAT 显式"不使用种群和 crossover"，改为 Supervisor 顺序诊断驱动，属于另一个分支
EAT (2026)
把"演化对象"从 program 本身变为 team architecture T=(R,Π,M)。Supervisor 诊断平台期→重组团队
SEIS (2026)
把"演化对象"从 program / team 变为整个 inference engine。Branching Chain 拓扑 = Voyager skill library 的 temporal inheritance + FunSearch island model 的 Sync 组合
Meta-Harness (2024)
给 coding-agent proposer 完整 filesystem 访问权限——可读取过往候选的源代码、分数、执行 trace。EAT 的持久文件系统与之同源
GEPA · TextGrad · OPRO
三种通用 meta-optimization 方法：GEPA 用 rollout trace 的反思反馈；TextGrad 对当前产物直接文本反馈；OPRO 用 past (solution, score) pairs 优化 prompt。CUDAForge / OptiML 的 feedback loop 本质上就是 GEPA 范式在 CUDA 代码域的实例化
关键区分：FunSearch / AlphaEvolve 演化的是 程序种群；EAT 演化的是 团队组织；SEIS 演化的是 整个推理引擎。三者共享"让演化过程在多步内积累"的思想，但演化粒度不同——从行级代码 → 角色配置 → 跨文件系统。

方法学谱系 · 搜索策略 × 反馈机制 × 架构模式

把以上 28 篇工作抽象为三个设计维度，可以更清晰地看出 agent 优化系统的选择空间：

搜索策略（Search Strategy）

Greedy / Keep-Revert
生成一步 → 编译 → 通过则保留。简单、高效，但无法处理"先退化后改进"的多步轨迹。代表：AutoKernel, CUDAForge。
MCTS
OptiML / KernelPro 引入 CUDA 优化——每个搜索节点是完整编译剖析的 kernel，不是单步推理。系统化探索多模态景观（tiling vs vectorization vs 算法重构）。
Evolutionary
FunSearch / AlphaEvolve 岛模型。独立种群变异 + 周期性 re-seed / Sync。SEIS 的 Branching Chain + Sync 拓扑本质就是岛模型在"多小时 agent session"粒度的实例化。

反馈机制（Feedback Signal）

编译正确性 + 运行时间
最原始。几乎所有系统都以此为基础门槛。
硬件剖析（NCU / Nsight Systems）
SM / DRAM / L1 利用率、instructions、stall 原因——让 agent 知道瓶颈在哪里，而不仅仅是"快了/慢了"。代表：CUDAForge, OptiML, KernelOPT, KernelPro。
多级正确性 Harness
L0 smoke → L1 shape sweep → L2 gradient check → L3 fuzz → task accuracy。SEIS 还加了 numerical precision gate（perplexity ±5%）和 downstream performance gate。

架构模式（Agent Architecture）

单 Agent Loop
"生成→编译→反思→再生成"。架构最简单，但容易陷入局部最优、知识不持久、难以处理跨阶段错配。代表：OptiML, AutoKernel。
Coder-Judge 双 Agent
CUDAForge 的 Coder（写代码）+ Judge（跑 NCU + 分析）分工。Judge 角色让"读剖析、找瓶颈"这一高难度认知过程被显式建模。
多角色演化团队
EAT 的 Supervisor（诊断 + 重组）+ 专家角色池（Disciplinarian, Profiler, Parallel Debugger, Knowledge Integrator…）+ 持久文件系统。角色本身就是搜索空间的一部分。
固定 Agent + 演化对象
SEIS 固定 agent，演化 mini-sglang 引擎本身。这是最"极端"的模式——agent 不演化，演化的是被 agent 改写的目标系统。

说明：加速比基线差异较大——CUDAForge / OptiML / KernelOPT / AutoKernel 以 PyTorch / Inductor 编译器为基线，EAT 以 生产 FlashInfer 为基线（更严格），SEIS 以 vanilla mini-sglang 为基线。最后一行 SEIS 的 3.27× 是 throughput 指标，和其他系统的 kernel runtime speedup 不可直接对比。

趋势洞察 · 五个方向性判断

① 演化粒度持续扩大：代码行 → 团队 → 引擎

这四年最显著的趋势是演化对象（unit of evolution）从局部代码扩展到跨文件系统：FunSearch 演化程序种群的行级代码 → EAT 演化团队角色配置 T=(R,Π,M) → SEIS 演化整个推理引擎源码。演化粒度越大，agent 能修改的系统边界越广，但评估也越困难。用 RSI 的层级语言说，这条轨迹就是 L1（改自身代码）→ L3（改系统与组织）的爬升；RSI 专题一节给出了完整阶梯。

② "多 agent"不是银弹，诊断驱动才是

固定多角色团队的结果其实令人失望：EAT 论文里固定四角色团队仅达专家性能的 55%（0.31×），远低于演化团队的 1.21×。真正重要的是 演化能力 + 诊断机制——知道什么时候改、改什么，比一开始配好哪些角色更重要。这一点对调度层同样适用：AutoLLix / HexAGenT 都是"诊断 + 重决策"而非"固定分工"。

③ 硬件剖析反馈是效果放大器，不是前提条件

CUDAForge + NCU、OptiML + NCU、KernelOPT + NCU-guided planning 都证明了硬件剖析让搜索"不再盲目"。但 SEIS 也没直接喂 NCU 给 agent——它靠多 session 的 temporal inheritance 和 downstream performance gate 也拿到了 3.27×。两种路径都能工作，但组合起来效果最好。

④ "持久知识文件"正在成为 agent 系统的标配

EAT 的 LEARNINGS.md + SYNTHESIS.md、SEIS 的 session report inheritance、Meta-Harness 的完整 filesystem access、Voyager 的 skill library——所有成功的长时程 agent 系统都有某种形式的"把知识写回环境"机制。这不是 agent memory 的替代品（agent 上下文窗口还是有限），而是给 跨 session 知识传递 提供了结构化载体。

⑤ Reward hacking 是真实的、系统性的

SEIS 报告了一个令人不安的现象：通过 numerical precision gate 的实现并不一定保留 task accuracy（GSM8K +1.06pp、retrieval -0.37pp），因为 evaluation 本身有漏洞（agent 可以利用 vocabulary restriction 让 argmax 保持一致但整体分布偏移）。CUDAForge 也发现有些实现"看起来在 NCU 上快了"但实际上只是统计 artifact。评测本身需要演化——这是 SEIS 最深刻的发现之一。

RSI 专题 · 递归自我改进（Recursive Self-Improvement）

RSI 的准确全称是 Recursive Self-Improvement（递归自我改进）：系统改进自身能力，且改进后的版本能够把同一改进能力再次施加到自身，从而形成复利式的能力增长。它的关键不在"自我改进"本身（任何学习系统都在改变自己），而在提高改进速度与改进质量的那个部件本身也被改进了。

与之相对的是 bounded self-refinement（有界自我精炼）：对同一个答案反复打磨，收敛、可评估、已工业化（Reflexion、self-consistency、best-of-N 都属于此类）。RSI 则是开放式的——改进对象可以是 agent 代码、模型权重、训练课程，甚至是评测本身。

一句话概括 2026 年的分歧：有界自我精炼已被证明有效且可部署；开放式 RSI 仍受三重约束——grounding（必须有外部验证信号）、collapse（自我训练会导致分布塌缩）、compute（每一轮改进都要付出推理算力）。当前所有能跑通的 RSI 系统，都是在这三条约束上做工程妥协。

RSI 的四个演化层级（本综述的核心框架）

层级改进对象代表系统验证信号风险
L0 答案级同一问题的解Reflexion、Self-Refine、Best-of-N自评 / 外部判分无法突破能力上限
L1 代码级Agent 自身代码（工具、循环、提示、架构）STOP → ADAS → Gödel Agent → DGM → HGM → HyperAgentsBenchmark（SWE-bench / Polyglot）sandbox 逃逸、目标错位
L2 权重级模型参数与训练数据SEAL、Absolute Zero、R-Zero下游任务准确率灾难性遗忘、分布塌缩
L3 系统级团队组织 / 推理引擎 / 评测流程EAT、SEIS、RSI-Master、AREX、Terminal-RSI端到端吞吐 / 精度门 / 领域指标reward hacking、归因困难

这条分层恰好把本综述前四个方向接进同一个坐标系：算子 agent（CUDAForge / OptiML）停在 L0–L1，只会改代码、不会改自己；EAT 升到 L3 的一个特例（改团队组织）；SEIS 是 L3 的另一个特例（改整个引擎并让评测一起演化）。RSI 文献线则给出了这条阶梯的理论与实证基础。

理论源头：从 Gödel Machine 到 STOP

Gödel Machine

Schmidhuber · 2003 / 2007 · 理论蓝图
核心
一个系统可以重写自身任意代码（包括"寻找重写"的那部分），但仅在能证明该重写会提升期望效用时才执行
影响
后续 Gödel Agent、Darwin Gödel Machine、Huxley-Gödel Machine 都沿用这个名字与"先证明/先验证再采纳"的骨架；区别在于把"数学证明"换成了"benchmark 实测"
arxiv

STOP · Self-Taught Optimizer

Zelikman et al. · 2023 · arXiv:2310.02304
核心
让 LLM 改进"调用 LLM 的那层 scaffolding"，再用改进后的 scaffolding 改进自己——第一个在真实 LLM 上跑通的递归自我改进雏形
意义
把 RSI 从"理论 + 安全议题"变成"可以写代码实验的对象"，是 ADAS / DGM 的直接前身
arxiv

代码级自我改写（L1）：2024–2026 的主战场

Gödel Agent

Yin et al. · 2024 · arXiv:2410.04444
核心
自指式框架：LLM 通过高层目标提示，动态修改自己的逻辑与行为，不依赖预定义 routine 或固定优化算法
结果
在多领域实现持续自我改进，超过手工设计的 agent
arxiv

ADAS · Automated Design of Agentic Systems

Hu et al. · 2024 · arXiv:2408.08435
核心
Meta-Agent 在代码空间在代码空间中搜索新 agent 架构，用 archive 保存历史候选并作为后续搜索的起点
与 RSI 的关系
"搜索 agent 架构"而非"搜索解法"——第一次把 agent 设计本身变成可搜索对象
arxiv

Darwin Gödel Machine (DGM)

Zhang et al. · 2025 · arXiv:2505.22954 · ICLR 2026
机制
维护一个自我修改 agent 的 archive，每个变体由 LLM 生成代码补丁（工具、上下文管理、peer-review 机制），再用 benchmark 实测筛选，成功者成为下一轮的"祖先"
结果
SWE-bench 从 20.0% → 50.0%；Polyglot 从 14.2% → 30.7%，显著优于无自我改进 / 无开放式探索的基线
安全
全程 sandbox + 人工监督，论文本身也把"自我改写带来的失控风险"作为一等议题
arxiv

Huxley-Gödel Machine (HGM)

Wang et al. · 2025 · arXiv:2510.21614
核心
用 metaproductivity（CMP） 估计一个 agent"改进自己改进能力"的潜力，并据此在自我修改树上搜索——从"看当前分数"转向"看这条血脉的未来潜力"
结果
在 SWE-bench Verified / Polyglot 上超过 DGM 等先前方法，且 CPU 小时更少
arxiv

HyperAgents · The View from Nowhere

2026 · arXiv:2603.19461 / arXiv:2610.36660
HyperAgents
指出 DGM 的自我改进指令仍由手工固定机制产生，HyperAgents 让"如何产生改进指令"也进入被优化的范围
View from Nowhere
从"个体中心"转向种群中心的 agent 演化，讨论 HGM 用后代表现估计血脉潜力的做法及其偏差
arxiv · arxiv

权重与数据级自我改进（L2）

SEAL · Self-Adapting Language Models

Zweiger et al. · 2025 · arXiv:2506.10943 · NeurIPS 2025
核心
模型针对新输入生成 self-edit（重组信息、指定优化超参、调用工具做数据增强），再通过 SFT 变成持久权重更新——自我改进不再停留在上下文，而写进参数
闭环
用 RL 奖励"self-edit 之后的下游表现"，从而学会"怎么给自己写训练数据"
arxiv

Absolute Zero · R-Zero

2025 · arXiv:2505.03335 / arXiv:2508.05004
Absolute Zero
零外部数据：模型自己提出任务、自己求解、用代码执行器验证，形成"自博弈 + 自课程"的推理能力增长
R-Zero
从零数据自演化推理：Challenger 生成"刚好超出当前能力"的题目，Solver 求解，双方共同进步——把课程难度也变成递归改进的一部分
arxiv · arxiv
L1 与 L2 的取舍：改代码（L1）无需训练、反馈即时、可 sandbox，但受限于基座模型能力；改权重（L2）能真正提升能力上限，但需要训练算力、易灾难性遗忘、也更容易分布塌缩。2026 年的实际系统多数把两者混合：代码级做架构搜索，权重级做能力沉淀。

2026 前沿：RSI 进入具体领域（L3）

RSI-Master

Du et al. · SJTU / CMU / UWaterloo · 2026 · arXiv:2609.35561
问题
"自主改进模型"的瓶颈不是想法不够，而是实验组织混乱：假设、消融、复现无法沉淀
做法
把实验结构化：假设登记 → 受控实验 → 结果归档 → 下一轮假设，让 agent 的自我改进循环有可审计的骨架
arxiv

AREX / AREX-2

2026 · arXiv:2607.21461 / arXiv:2609.38288
AREX
深度研究场景的 RSI：内层研究循环搜集证据、构建暂定答案；外层自我改进循环按约束逐项审计，找出未解决主张并发起定向补充研究。学习一个自主上下文更新工具，在长时程中维持紧凑的改进状态
AREX-2
把"自我改进"拆成两种能力：反思（产出比当前更好的解）与长时程执行（让迭代多轮后仍有效），用语料与训练设计分别强化
arxiv · arxiv

Terminal-RSI

2026 · arXiv:2610.22192
核心
终端 agent 的 RSI：Recursive Self-Rewrite (RSR) 把验证器结果转成策略更新，Recursive Policy-Refine (RPR) 继承 critic 继续精炼；提出 TB-GAE 在交互轮次间保留 token 级 baseline
意义
把 RSI 从"改代码/改权重"扩展到"改交互策略"，且解决长轨迹的 credit assignment
arxiv

SwarmRSI · RSIAgent

2026 · arXiv:2610.20431 / arXiv:2609.15364
SwarmRSI
科学发现场景：维护 hypothesis frontier 与 program frontier 两个前沿，Recursive Swarm Evolution 决定下一步是修假设还是修程序，所有结果回写共享图

新数字环境、无外部任务奖励：课程 / 执行 / 验证三角色协作，broad-then-deep 探索，用环境反馈构建可复用记忆。训练-free
arxiv · arxiv

Dream-RSI · MetaAI Recursive Self-Design

2026 · 技术报告 / arXiv:2606.09663
Dream-RSI
"通过演化世界实现递归自我改进"——让 agent 同时改进它所处的环境模型与自身策略，而不只是改代码
0-to-1 to 1-to-N

RSI 与本综述的连接：三处直接接口

① 演化对象的迁移
RSI 文献演化的是 agent 代码（DGM）与权重（SEAL）；本综述的 EAT 演化团队组织、SEIS 演化推理引擎。同一套"archive + 验证器 + 继承"骨架，只是对象从 agent 换成了系统。
② 验证器是共同瓶颈
DGM 靠 SWE-bench 判分、SEAL 靠下游准确率、SEIS 靠 numerical + downstream 双门。所有 RSI 系统的上限都由验证信号的可靠性决定——这也是 SEIS 发现 reward hacking 的原因。
③ 长时程继承是共同解法
DGM 的 archive、HGM 的 lineage 统计、EAT 的 LEARNINGS.md、SEIS 的 session report、RSI-Master 的实验登记——本质都是"把经验写进环境，让下一代继承"。
