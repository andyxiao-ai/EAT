

### Evolving Agent Teams



### Abstract

The rapid progress of software engineering agents drives interest in applying them to open-ended problems such as GPU kernel optimization. However, we find that existing coding agents converge to local optima on real-world, expert-written kernels (e.g., FlashInfer). We introduce Evolving Agent Teams, a multi-agent framework that escapes such local optima. It features (1) a central supervisor that diagnoses each local optimum and restructures a team of agents; and (2) a persistent file system that comprises a learning document, an evolution history, and per-team artifacts, grounding restructuring with accumulated experience. Under a matched token budget, Evolving Agent Teams consistently outperforms strong coding-agent baselines. With an extended token budget, Evolving Agent Teams generates a CUDA kernel that reaches [1.2\times] mean speedup over the production FlashInfer MLA paged decode kernel from scratch and wins on 36 of 47 production workloads from FlashInfer-Bench ( [0.86] – [0.99\times] on the remaining 11). It also demonstrates superior performance on tasks such as KDA prefill on AMD MI350X ( [3.01\times] over vLLM) and NVIDIA B200 ( [3.44\times] over FlashKDA), MoE expert-offload serving on Apple silicon ( [30.3] tokens/s decode for Qwen3.8-Flash-Next in MLX 4-bit on a 48 GB M4 Pro), and RoboDojo robot manipulation ( [62.1] on held-out seeds vs. [55.3] for the best leaderboard entry). Code is available at https://github.com/caoshiyi/EAT.

### 1 Introduction

The rapid progress of coding agents on software engineering tasks [15, 42, 38] has driven interest in applying them to open-ended discovery tasks such as GPU kernel optimization. Here, the goal is not just to produce a correct kernel but to search a large, hardware-dependent design space for high performance. Expert-written kernels such as FlashInfer [46] and FlashAttention [31] navigate this space across two levels: low-level primitive use (e.g., WGMMA tensor cores, swizzled shared-memory layouts) and high-level architectural design (e.g., dispatch strategies, warp specialization, dataflow). While low-level primitive use can substantially improve performance within a chosen design, high-level architectural choices often determine which hardware bottlenecks remain and thus largely shape the attainable performance ceiling.
Unfortunately, even strong coding agents struggle to write challenging GPU kernels. They often make rapid initial progress, but then converge to local optima far below expert-written baselines. A common failure mode is that agents select design directions that are initially easier to implement but architecturally limited, spend most of their budget tuning within those directions, and fail to revisit harder alternatives that require substantial debugging or architectural rethinking.
For example, when writing the MLA decode kernel used in DeepSeek-V3 inference [10], single-agent runs often abandoned difficult WGMMA-based implementations after repeated correctness failures, and instead optimized simpler but less efficient WMMA-based designs. These designs plateaued far below expert-written baselines: Codex 5.5 xHigh reaches only 28% of expert performance despite a $1K budget and multiple days of effort. Static agent teams show the same limitation (Section 4): a fixed 4-role team built with Claude Code [2] Opus 4.7 1M reaches only 55%. These results suggest that neither stronger single agents nor fixed teams are sufficient for challenging GPU kernel optimization. The process moves through distinct phases, from establishing correctness to debugging hardware primitives, profiling bottlenecks, and redesigning the kernel architecture. Each phase requires different expertise, tools, and coordination patterns, causing fixed agent organizations to become mismatched to the current stage.
We introduce Evolving Agent Teams, a multi-agent framework that escapes such local optima by evolving the agent team’s organization alongside the optimization process. This evolution is driven by a central supervisor agent, grounded in a persistent file system with accumulated experience. Concretely, the supervisor monitors team progress, reflects on the agent behavior, diagnoses the cause of plateau (e.g., a knowledge gap or an exhausted search), and adapts the team accordingly: spawning specialists for high-effort tasks, introducing profiling roles to get more insights, or running parallel roles for different directions (Section 3.2). The file system contains a learning document of empirical observations, per-team artifacts, and an evolution history.
On the MLA decode kernel, Evolving Agent Teams explores over 100 team configurations. The supervisor repeatedly reconfigures the team around the current failure mode, which improves token efficiency and enables successive architectural advances, including performant WGMMA-based matrix multiplication, a PV accumulation strategy, and L2 prefetching. Together, these improvements allow Evolving Agent Teams to substantially outperform prior single-agent and static-team approaches (Figure 1).
We evaluate on four challenging CUDA kernel optimization tasks spanning two GPU architectures (Section4): Flash Attention 4 [49] and Gated Delta Net [43] prefill on Blackwell B200, and MLA paged decode [10, 46] and fused GEMM+AllReduce (G+AR) [35] on Hopper H100. Evolving Agent Teams outperforms strong coding agent baselines on every task. Notably, on the MLA paged decode task, evaluated on 47 production DeepSeek-V3 workloads from FlashInfer-Bench [11], Claude Code agent plateaus at [0.51\times] the expert-written FlashInfer kernel, while our system reaches [0.74\times] under a matched token budget. With additional budget, the system surpasses the production FlashInfer baseline, achieving [1.21\times] mean speedup , faster on 36 of 47 workloads, while the previous best result is [0.61\times] from K-Search [5].


### 2 Related Work

Multi-agent LLM systems. ChatDev [29], MetaGPT [13], and MAGIS [36] assign fixed roles (programmer, reviewer, tester) to distinct agents for software engineering. AutoGen [40] provides a general multi-agent conversation framework; DyLAN [22] and AgentVerse [9] dynamically adapt the team’s role composition during execution, but either select from a hand-crafted pool of role prompts (DyLAN) or regenerate the group from scratch each round without preserving global context across re-compositions (AgentVerse). Our framework differs in two respects: (1) it operates over multi-day horizons where the nature of productive work changes qualitatively (from knowledge acquisition to search to verification), requiring changes to agent roles and mandates, not merely routing; and (2) the supervisor maintains a persistent global file system across team restructurings.
Self-improving agents and evolutionary search. Reflexion [33] accumulates verbal feedback across trials; Voyager [37] builds a growing skill library. These approaches improve a single agent’s behavior within a fixed role, whereas our framework adapts the broader optimization process around a single agent. FunSearch [30], OpenEvolve[32] and AlphaEvolve [24] use population-based evolutionary search with LLM-driven mutation over programs. Our approach differs in that it employs no population and no crossover; instead, a supervisor performs sequential, diagnosis-driven adaptation of the agent team architecture. ADAS[14] uses an LLM with an archive to iteratively propose new agent architectures. Our work also uses an LLM to iteratively adapt the team architecture. However, the purpose of this adaptation is different: rather than searching for a standalone best agent architecture, we evolve the team to better facilitate the optimization process at different stages.
Meta-optimization and text optimization. A growing body of work uses LLMs to optimize text and code artifacts iteratively. OPRO [41] optimizes prompts conditioned on past (solution, score) pairs; TextGrad [48] provides textual feedback on current artifacts; GEPA [1] uses reflective feedback from rollout traces. Meta-Harness [19] optimizes the code surrounding a fixed LLM by giving a coding-agent proposer full filesystem access to prior candidates’ source code, scores, and execution traces. Our work shares the insight that richer access to prior experience enables better meta-optimization. However, the object of optimization is different: Meta-Harness optimizes the surrounding harness, whereas our method adapts the search process itself to better discover high-performance kernel implementations.
Code generation and optimization, and inference-time scaling. SWE-agent [42], SkyRL-Agent [4] and SWE-Gym [27] advance agents in software engineering tasks. In GPU kernel optimization, most of the existing LLM-based solutions [39, 18, 21, 50] adopt a fixed human-designed system, where LLMs refine kernels based on compilation or profiling feedback. Some recent works [12] add evolutionary strategies into the system for maintaining and selecting candidates. K-Search [5] decouples planning from implementation via a co-evolving world model but employs a fixed two-role configuration. Inference-time compute scaling [34, 20] improves reasoning within a fixed inference-time search procedure; our framework addresses the complementary problem of adapting the search process itself.


### 3 Method

Figure 2: The Evolving Agent Teams framework. Team execution runs coding agents on the task through tool use and execution feedback. Team evolution acts as a meta-optimizer: it analyzes the past success and failure patterns, and adapts the team composition, role specialization, coordination protocol, and knowledge management for the current stage of discovery.


### 3.1 Problem Setup

We consider open-ended program optimization tasks: given a goal description, a codebase, and correctness constraints [\mathcal{C}] , find a solution [s\in\mathcal{P}] (an executable program) that maximizes a scoring function [\mathcal{F}:\mathcal{P}\to\mathbb{R}] while satisfying [\mathcal{C}] . Performance is measured against a finite token budget.
Existing LLM-based systems tackling this problem [42, 3, 29, 13, 30, 24, 7] can be characterized by an agent team configuration [T=(R,\Pi,M)] governing three design choices:
Roles [R] — what each agent is responsible for, e.g., a single generalist [42, 26, 2], fixed programmer/reviewer/tester [29, 13], or an LLM mutation operator [30, 24, 7].
Coordination [\Pi] — how agents interact, e.g., no coordination (single agent), a fixed role-to-role pipeline [29, 13], or a select-mutate-evaluate cycle [30, 24, 7].
Knowledge management [M] — how experience is accumulated and shared, e.g., the filesystem with no explicit management [42, 2], structured message passing enforced by fixed protocol [29, 13], or a candidate archive [30, 24, 32, 7].
In most existing frameworks, all three are human-designed and fixed before the run begins.11 1 Some evolutionary systems adapt search hyperparameters during a run (e.g., AdaEvolve [7] modulates exploration intensity and budget allocation); here “fixed” refers specifically to the team configuration [T=(R,\Pi,M)] , the roles, coordination protocol, and knowledge management strategy, which remain static in all listed systems. These systems optimize the solution [s] but do not adapt [T] itself, making them prone to stagnation at local optima during long-running open-ended optimization tasks.


### 3.2 Evolving Agent Teams

Evolving Agent Teams co-evolves [T] alongside [s] , adapting the optimization system to better facilitate the discovery. It operates at two levels, following the loop shown in Figure 2: at the team evolution level, a supervisor agent monitors each team’s execution, analyzes success and failure patterns, and designs the next team [T_{v+1}] . At the team execution level, a team of LLM-based coding agents works on the task under the current configuration [T_{v}] . A persistent file system [K] connects the two levels, accumulating all records across team executions and restructurings: a learnings document of accumulated empirical observations, per-team artifacts (kernels and per-role records), and the evolution history (the supervisor’s reflections and design decisions from each version), so that each team can build on and improve upon prior work.


### Team Evolution.

The supervisor is triggered by two signals: the current team finishing its run, or a fixed-interval cron job. Upon either, it checks the team’s progress so far, reflects on any observed failure or success patterns (e.g., drifting to easy paths, key insights from previous teams lost, stuck in debugging, and heavily micro-optimizing), and designs the next team along the three axes of [T] :
Roles. The supervisor invents roles as needed, rather than selecting from a predefined set. A single agent handling implementation, profiling, and research simultaneously divides its limited context across all three, sacrificing depth in each. The supervisor addresses this by creating focused roles such as Profiling Scientist (designs targeted microbenchmarks to isolate bottlenecks), Challenger (stress-tests claimed performance ceilings), Primitive Study Agent (studies potentially useful primitives and their usage, running small tests), and Knowledge Integrator (synthesizes findings scattered across prior teams into actionable plans). Table 3 in the appendix lists other observed roles.
Coordination. The supervisor decides how agents interact: it can pipeline them (research [\to] implement [\to] profile), run them in parallel on separate branches, or combine both. For example, the supervisor may spawn one agent solely to debug a blocking issue (forbidden from touching the main codebase) while a second agent continues optimizations on the main branch, so that one agent’s failure does not block the other’s progress.
Knowledge management. The supervisor evolves how teams manage their experience and learning within the file system [K] , specifying where each agent should output: e.g., write findings into a dedicated document, append learnings during execution to a team-shared log, or commit code to a specific branch. For example, when early insights were getting lost across teams, the supervisor introduced a cross-agent synthesis document that connected all prior findings into an actionable plan, and mandated future teams to read it.


### Team Execution.

Each team execution deploys the agents specified by [T_{v}] on the task. Each agent is an LLM-based coding agent [42, 3] with shell access, able to read and write files, execute commands, run compilers and profilers, and iterate autonomously on the codebase. Agents receive their role mandates and access to the codebase, evaluation tools, and the file system [K] . One agent’s outputs (committed code, profiling reports, written analyses) become inputs for others according to the coordination plan.


### File System.

The file system [K] is a shared filesystem that persists and grows across all team versions. [K] contains the codebase, evaluation tools, and all records produced by prior teams: the learnings document, per-team artifacts (kernels and per-role records), and the evolution history. This continuity is critical for long-running optimization: each team inherits all prior learnings, failed attempts, and successful strategies, enabling continuous experience accumulation that may open up new optimization directions.

### 4.1 Experimental Setup

Tasks. We evaluate on four GPU kernel optimization tasks spanning two architectures (Table 1). FA4 targets the attention forward pass [49], written in CuTe DSL [6]; the challenge is co-designing algorithm and kernel pipelining for Blackwell’s asymmetric hardware scaling, where tensor core throughput doubles but shared memory bandwidth and non-matmul units do not. GDN computes a prefill pass for Gated DeltaNet [43], a linear RNN with a matrix-valued hidden state; the challenge is parallelizing the inherently sequential recurrence over long sequences via a chunkwise algorithm. MLA implements paged decode for DeepSeek-V3’s Multi-head Latent Attention [10]; the challenge is overlapping CUDA core and tensor core work efficiently under extreme register pressure due to MLA’s large head dimension. G+AR fuses GEMM with inter-GPU AllReduce into a single kernel, overlapping computation and communication; efficient fusing requires writing a custom WGMMA GEMM kernel with tile-level scheduling to overlap reduction with compute.
Metrics. For each task, we report the speedup relative to the production baseline: the geometric mean of [t_{\text{base}}/t_{\text{kernel}}] across a set of workloads, where [t_{\text{base}}] and [t_{\text{kernel}}] are the baseline and optimized kernel latencies respectively. Values above [1.0\times] indicate the optimized kernel is faster than the baseline; values below [1.0\times] indicate it is slower. All settings are run twice; we report the best result from each pair. We acknowledge this limits statistical conclusions and discuss implications in Section 5.
Workloads. GDN prefill and MLA workloads are drawn from FlashInfer-Bench [11], which provides representative production serving shapes. FA4 workloads use the same shapes as used in the performance report in the FlashAttention-4 paper [49]. GEMM+AR (G+AR) workloads are taken from the ThunderKittens benchmark suite [35].
Baselines. We compare against three baseline systems. (1) Claude Code [2]: Claude Code powered by Claude Opus 4.6 with 1M context window, a state-of-the-art coding agent with file editing, shell access, and compiler invocation that autonomously writes, compiles, profiles, and iterates on kernel code. It receives the same task description, reference kernel, and test harness as the evolving team. Evaluated on all four tasks in the budget-controlled experiment (Section 4.2). (2) Fixed four-role team: a static team of four common high-value roles for GPU kernel optimization (Profiler, Hardware Researcher, Planner, Implementer), each powered by Claude Code with the same Opus 4.7 1M model, but with no supervisor and no team restructuring. Evaluated on MLA in the ablation study (Section 4.5). (3) Codex [26]: a strong coding agent powered by GPT-5.5 xhigh with 258K context. Evaluated on MLA in the ablation study (Section 4.5). (4) Kernel-specific systems: K-Search [5] and CUDAForge [50], run from their publicly released implementations with Claude Opus 4.6. Evaluated on MLA (Section 4.6). For Claude Code, K-Search, CUDAForge, and Evolving Agent Teams, we run each setting twice and report the best result; the fixed-team and Codex ablations are single runs.
Implementation. Evolving Agent Teams is built on top of Claude Code [2] agents powered by Claude Opus 4.6 with 1M context. The supervisor is itself a Claude Code agent that orchestrates team evolution by spawning and monitoring worker agents. There are no predefined initial roles or team configurations; the supervisor designs all roles, coordination plans, and knowledge management strategies from scratch based on the task description.

Evolving Agent Teams outperforms Claude Code: Claude Code curves flatten early on FA4 and GDN Prefill, while Evolving Agent Teams continues improving with more budget spent. On MLA decode, Claude Code plateaus around [0.44] – [0.51\times] : it abandons the difficult WGMMA tensor core implementation after repeated failures at correctness and instead uses the WMMA API, which limits the tensor core utilization compared to WGMMA. The evolving team reaches [0.75\times] under the budget-controlled setting ( [1.21\times] with additional budget, as shown in Figure 1).
The GDN prefill panel shows particularly high speedups ( [>2\times] ) because the 100-workload benchmark includes many small input sizes where FlashInfer’s planning and preprocessing overhead dominates end-to-end latency, even with plan() cached across calls. Our generated kernel requires no planning stage, so on these small workloads it achieves disproportionately large speedups. Under the budget-controlled setting, the best Evolving Agent Teams run has a worst workload of [0.19\times] with 43 of 100 below the baseline, compared to [0.13\times] and 49 of 100 for the best Claude Code run. With additional budget (Section 4.3), the worst workload improves to [0.40\times] with 37 of 100 below the baseline.
On GEMM+AllReduce, the single-agent run produces a cuBLAS-based kernel, yielding a mean speedup of [1.08\times] compared to the cuBLAS + NCCL baseline. The budget-controlled evolving team similarly converges on a cuBLAS+NCCL pipeline, achieving [1.18\times] with stronger gains at larger matrix sizes (32K: [1.34\times] ). With additional budget (Section 4.3), the team discovers a fused WGMMA+NVLS kernel that bypasses cuBLAS entirely and leverages NVLink multicast for the all-reduce, reaching [1.49\times] overall and [2.57\times] on the smallest workload where communication latency dominates.
Across all four tasks, the best Evolving Agent Teams kernel matches or exceeds the best Claude Code kernel on nearly every workload (Figure 3(b)), with a single exception on MLA decode. This broad coverage suggests the system does not overfit to a narrow regime; we attribute it to the supervisor’s tendency to evolve roles such as Workload Analyst that explicitly diagnose per-workload regressions and steer optimization toward balanced performance (Appendix A).

Beyond the budget-controlled comparison, we ran Evolving Agent Teams with additional token budget on GDN and G+AR (Figure 4).
GDN Prefill (Figure 4(a)) continues to improve from a [2.2\times] kernel to [4.06\times] mean speedup across 21 team versions. Versions 6–10 introduce TMA asynchronous loads and a warp-specialized pipeline that first exceeds the baseline ( [1.08\times] ). Versions 15–22 shift to a fundamentally different architecture: the team replaces cuBLAS with a custom WGMMA kernel fused with NVLink multicast for the all-reduce, culminating in cluster-level TMA multicast ( [1.56\times] ).


### 4.4 Optimizing an Already-Optimized Implementation

(a) Evolution trajectory.
(b) Benchmark grid: latency comparison (ours vs. Triton).
Figure 5: Flash-KMeans (H100). (a) Evolution trajectory; each point is one kernel version. (b) Per-iteration latency comparison across the paper’s benchmark grid ( [D{=}128] , FP16). Our CUDA WGMMA kernel achieves up to [1.5\times] lower latency on compute-bound configurations (high [K] ), while matching Triton on memory-bound regimes.
The four tasks above start from naïve reference kernels. To test whether Evolving Agent Teams can also improve code that has already been carefully optimized by domain experts, we apply it to Flash-KMeans [45], a recent GPU-optimized exact K-Means implementation. Flash-KMeans fuses distance computation with online argmin (FlashAssign) to bypass HBM materialization of the [N{\times}K] distance matrix and introduces a sort-inverse update that transforms high-contention atomic scatters into segment-level localized reductions, achieving up to [17.9\times] end-to-end speedup over prior GPU baselines on H200. The released implementation uses hand-tuned Triton kernels. We task the Evolving Agent Teams with rewriting the assignment kernel in CUDA, starting from the Triton source as a reference rather than a naïve PyTorch baseline. As shown in Figure 5, the system produces a CUDA WGMMA kernel that reaches [1.71\times] speedup over the Triton kernel on the default workload, and achieves up to [1.5\times] lower latency on compute-bound configurations (high [K] ) across the full benchmark grid (Figure 5(b)).


### 4.5 Ablation Studies

Figure 6: Ablation on MLA decode.
Figure 6 compares Evolving Agent Teams against two ablation baselines on MLA decode. The fixed four-role team (Profiler, Hardware Researcher, Planner, Implementer) reaches [0.31\times] : role specialization helps early on, but the static configuration cannot adapt when the optimization landscape shifts, e.g., it lacks a Knowledge Integrator to prevent cross-agents information asymmetry or a Challenger to break premature ceiling declarations (examples provided in Appendix B). Codex (GPT-5.5 xhigh, 258K context) reaches [0.28\times] , confirming that the gains of Evolving Agent Teams ( [0.74\times] ) are not solely due to model choice. The [0.31\times\to 0.74\times] gap between the fixed team and the evolving team isolates the value of team evolution: both use the same model and multi-agent structure, but only the evolving system can restructure roles and coordination in response to diagnosed failure modes.

### 5 Conclusion

Strong coding agents make rapid initial progress on GPU kernel optimization but converge to local optima well below expert-written baselines. Evolving Agent Teams escapes these local optima by evolving the team’s organization alongside the search: a central supervisor diagnoses each plateau and restructures the team’s roles, grounded in a persistent file system. Across four CUDA kernel optimization tasks on Hopper and Blackwell GPUs, it consistently outperforms strong coding-agent baselines under a matched token budget, and with additional budget it surpasses the production FlashInfer MLA decode kernel at [1.21\times] mean speedup across 47 workloads. It also demonstrates superior performance on tasks such as KDA prefill on AMD and NVIDIA GPUs, MoE expert-offload serving on Apple silicon, and robot manipulation.
Limitations. We run each main setting twice and each setting in Section 4.7 once, which limits statistical comparisons; a cost-vs-performance Pareto analysis and a controlled study of noisier domains remain future work.

### Appendix B Case Study: Why the Fixed Four-Role Baseline Starts Slowly

Figure 6 shows the fixed four-role baseline (Planner, Hardware Researcher, Implementer, and Profiler; all Claude Opus 4.7, coordinating through a shared filesystem and a SendMessage primitive) reaching its first correctness-passing commit substantially later than the single agent on MLA decode. Most of this delay is traceable to a single class of bug: a low-level SMEM-layout mismatch in which WGMMA on SM90 requires [8\times 64] atom-tiled shared memory, but the Implementer wrote row-major tiles, silently corrupting the QK output.
The information needed to identify the bug is present in the team but partitioned across agents: the Hardware Researcher holds the layout requirement, the Implementer holds the actual SMEM declaration, and both agree on the descriptor numerics, leading them to localize the bug elsewhere. The team iterates through incorrect hypotheses without any agent reading the Implementer’s source to inspect the layout, despite all having Read access. A single agent holding both specification and code in its context would identify the discrepancy on direct inspection.
The failure is structural rather than capability-driven. Each role’s charter implicitly scopes its outputs (the Hardware Researcher operates as a recipe expert, not an auditor); spawn prompts specify reactive behavior, locking roles into question-and-answer loops that preclude proactive code inspection; and the SendMessage primitive carries prose, encouraging abstract agreement (“LBO=16, confirm?”) over byte-level cross-checking. Fixed-role multi-agent systems can therefore stall on debugging tasks that cross role boundaries. Evolving Agent Teams addresses this class of failure: the supervisor diagnoses the stall as a knowledge gap and introduces a Knowledge Integrator (Section 3.3) that mandates cross-agent artifact reads.


### Appendix C Details of the Additional Settings

All four runs use the same supervisor prompt and harness as the main experiments, with no predefined roles. Each is a single run, so we report them as case studies rather than controlled comparisons; the matched-budget solo ablations are in Appendix D. Costs are booked agent and supervisor API spend at published per-token prices.
KDA prefill on AMD MI350X. Kimi Delta Attention [16] is a gated delta rule with a per-key-channel forget gate and a matrix-valued fp32 state; the kernel computes the chunked prefill from the raw projections (normalization, gates and recurrence). The task uses one MI350X (CDNA4) and the tensor-parallel shape of a production deployment ( [H{=}12] heads per GPU, [K{=}V{=}128] ). The baseline is vLLM’s hand-written fused HIP prefill kernels used in production [17]; the starting kernel is a port of them (score [0.99] ). The score is the arithmetic mean of baseline-over-candidate latency across 10 variable-length workloads (single sequences of 1K–64K tokens, batches from [4{\times}4] K to [64{\times}128] , and one mixed batch), with the cache flushed before each timed run. Correctness requires relative [L_{2}] error [\leq 2{\times}10^{-2}] on outputs and final states; the team itself found that the evaluation’s fast-decaying gates let state-handoff bugs pass, and added a slow-decay check that every subsequent kernel had to pass, along with a held-out shape set that is checked but not scored. The run used Claude Opus 5.5 (medium effort) for all agents, lasted 73 iterations (186 hours), and booked $3.0K. The final kernel scores [3.01\times] (mean of five re-measurements; per-workload [2.09] – [4.63\times] ) and is [7.3\times] faster than the Triton kernel from Flash Linear Attention. Its main structural changes are a “relay” that fuses the prologue with the recurrence and passes the state between workgroups through the shared L2 cache, bf16/fp16 state handoffs and non-temporal loads, fp16 matrix operands ( [+5.5\%] and more accurate than bf16), and a “twin route” that feeds one 64-token recurrence step from two 32-token prologues.
KDA prefill on B200. The task is the same operator on B200 (sm_100a), scored as the geomean speedup over FlashKDA [23], a fused CUTLASS implementation, in a clean room with no web access. The team could read FlashKDA, the Triton KDA kernels of Flash Linear Attention, the CUTLASS/CuTe examples, FlashAttention-4 [49], and a read-only snapshot of FlashInfer [46] at commit a9e03bf2 (Aug. 13, 2026), which includes the SM100 KDA prefill kernels that CAKE [47] contributed to FlashInfer; the team ported these in the first iteration ( [1.96\times] ). The score covers six workloads (8,192 tokens, [H\in\{64,96\}] , fixed and variable-length layouts). Iterations 1–5 used Claude Opus 5.5 and later iterations Claude Sonnet 5.5. Comparison with KDA2. KDA2 [51] reports [2.96\times] over FlashKDA on B300 on the same six workloads. We recompiled the team’s final kernel for B300 (sm_103a, no code change) and scored it and KDA2’s released kernels with the same harness on the same B300: [3.54\times] for ours, against [3.02\times] (TIRx), [2.98\times] (PTX), and [2.85\times] (CuTe-DSL) for KDA2. On B200, the same harness gives [3.44\times] , against [2.91\times] (TIRx) and [2.74\times] (CuTe-DSL); the PTX kernels run only on B300. Because the run starts from a port of an existing kernel, it measures improvement over a strong start rather than from scratch.
MoE expert-offload serving on Apple silicon. The task is to make a Metal port of the FreeToken MoE serving system [44] serve Qwen3.8-Flash-Next at 4 bits (about 79 GB of weights plus a 32 GB per-layer embedding table; 512 routed experts per layer, top-10 plus a shared expert) as fast as possible on a 48 GB M4 Pro Mac, streaming experts that do not fit in memory from SSD through an offload cache. The model and math must stay the same: no expert skipping or pruning, no lower top- [k] , no fewer bits. Gates check top-1 agreement with the naive engine’s greedy predictions, KL divergence, peak memory ( [\leq 37] GiB), swap growth, and load time, and a candidate that fails any gate scores 0. The score is the mean over workload terms of baseline time over candidate time; the workload replays sessions recorded from a real coding-agent loop, teacher-forced from a cold page cache, plus a batch-1 decode benchmark. All agents used Claude Opus 5.5, with web search and fetch tools disabled. The supervisor resized the team from one agent to three and finally to two, and re-cut its roles six times: by file type (I/O vs. compute), by bottleneck (speculation, cache, offload), by time slice (decode vs. prefill), and by measured gap (GPU time per token). Main changes include a victim cache for evicted experts, compact GPU expert slots with shared palette indices, (scale, bias) palette compression that cuts expert reads by 7%, and admission rather than eviction as the residency lever, after a cache role found that most decode misses had already been read during the preceding prefill. The final engine decodes at [27.3] tokens/s on the batch-1 decode benchmark, against [13.4] for the naive engine. In Figure 7c, iterations 3–6 have no valid evaluation, and each iteration’s cost is its team cost scaled so that the total matches the booked $1.0K, which includes the supervisor.
RoboDojo. RoboDojo [8] has 42 dual-arm manipulation tasks in Isaac Sim, grouped into five dimensions (generalization, memory, precision, long-horizon, open-ended); the leaderboard score is the mean of the five dimension means of per-task partial-credit scores (0–100). The team edits a Python controller package with per-task skill modules. At run time the policy may call the frozen [\pi_{0.5}] checkpoint [28] and a runtime LLM (Claude, at most 20 calls per episode); inputs are three RGB cameras, joint states, and the instruction, and no model training is allowed. The agents’ outbound network is limited to the Anthropic API and the evaluation fleet, and other leaderboard entries’ policy code is removed from the hosts. Agents develop on seed 1; seeds 0 and 2 are held out and evaluated only by the operator, and agents never see those scores. Iterations 1–36 optimize a 10-task subset; iterations 37–51 use all 42 tasks. The supervisor and all agents used Claude Sonnet 5.5, and the run booked $472 through iteration 50 (excluding runtime-LLM calls). The iteration-50 policy scores [62.1] held-out (50 episodes per task on each held-out seed) and [62.6] on dev.
